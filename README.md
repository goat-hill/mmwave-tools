# mmwave-tools

Linux tooling for the TI **IWRL6844EVM** (xWRL684x) with the mmWave Low-Power SDK.
TI's flasher and visualizer ship as Windows `.exe` files; this repo provides Linux
equivalents and stays outside the SDK so SDK updates never overwrite it.

See [docs/profiles.md](docs/profiles.md) for the radar profiles and
[docs/learnings.md](docs/learnings.md) for what we found along the way (firmware quirks,
device test results, person detection and golf notes).

## Layout

```
mmwave-tools/
├── .venv/                  Python 3.12 (uv) — not committed
├── flash/
│   ├── extract_arprog.py   pulls TI's flasher bytecode out of the .exe
│   ├── run_arprog.py       runs that bytecode on Linux
│   └── extracted/          generated by extract_arprog.py — not committed
├── docs/
│   ├── profiles.md         every radar profile: settings, derived numbers, verification status
│   └── learnings.md        setup lessons, firmware quirks, device test log, person/golf notes
├── cfgs/                   your own .cfg files (listed in the visualizer as local/…)
├── visualizer/
│   ├── server.py           visualizer backend (aiohttp)
│   ├── web/                visualizer frontend (Vite + Svelte + TS)
│   ├── oob_protocol.py     cfg sender + data-UART frame parser (shared by everything)
│   ├── cfg_info.py         derived radar parameters from a .cfg (range/velocity res, ...)
│   └── stream_check.py     terminal tool: configure, print/log/replay frames
└── logs/                   raw data-port captures — not committed
```

## Setup

```sh
export MMWAVE_SDK=~/ti/MMWAVE_L_SDK_06_01_03_04/mmwave_l_sdk_06_01_03_04

cd ~/code/mmwave-tools
uv venv --python 3.12 .venv
uv pip install --python .venv pyserial idna
```

fish: `set -x MMWAVE_SDK ~/ti/MMWAVE_L_SDK_06_01_03_04/mmwave_l_sdk_06_01_03_04`

Python 3.12 specifically is required: TI's flasher is compiled 3.12 bytecode, which
only runs on the interpreter version that produced it.

If ModemManager is running, stop it while using the board
(`sudo systemctl stop ModemManager`). It probes new `ttyACM` ports and broke the
first flash attempt here (the bootloader never ACKed).

## Board

Connect only the **XDS110** micro-USB port (not FTDI). USB power is enough to flash
and run the OOB demo. Always power off (unplug) before changing SOP switches.

| Port | XDS110 interface | Use |
|---|---|---|
| `/dev/ttyACM0` (`…-if00`) | Application/User UART → UARTB | flashing, demo CLI (115200) |
| `/dev/ttyACM1` (`…-if03`) | Auxiliary Data Port → UARTA | demo data out (1250000) |

Your user must be in the `dialout` group to open these. `ls -l /dev/serial/by-id/`
shows which is which.

| Mode | SOP switches | Notes |
|---|---|---|
| Flashing | SOP0 = OFF/L, SOP1 = OFF/L | same in the SDK docs and EVM docs |
| Functional | per EVM docs: SOP0_H, SOP1_L | the SDK's generic table says SOP0 OFF, SOP1 ON; trust the EVM docs |

Other switches: **S1.4 = ON, S1.5 = ON** routes UARTA (demo data) to the XDS110.
The XDS110 firmware here is already 03.00.00.37, the SDK's UARTA-capable version,
so the SDK's "XDS Firmware Update" step isn't needed.

User LED 2 toggles every time the device wakes from deep sleep (`lowPowerCfg 1`),
i.e. it blinks once per frame while the sensor runs.

## Flashing

`tools/FlashingTool/arprog_cmdline_6844.exe` is a PyInstaller bundle of Python 3.12
bytecode (no `.py` source is shipped). The code itself is portable pyserial; the only
Windows-only pieces (`xds110reset.exe` for `-x`, FTDI d2xx for SOP control) are not
used by the normal flash command. So we extract the bytecode and run it under a 3.12
venv with Linux pyserial.

```sh
# once per SDK version
cd ~/code/mmwave-tools/flash
python3 extract_arprog.py            # uses $MMWAVE_SDK
../.venv/bin/python run_arprog.py --help

# board in flashing mode, then:
../.venv/bin/python run_arprog.py -p /dev/ttyACM0 \
  -f1 $MMWAVE_SDK/examples/mmw_demo/mmwave_demo/prebuilt_binaries/xwrL684x-evm/mmwave_demo.release.appimage \
  -s SFLASH -c -cf
```

- `-p` serial port, `-f1` image, `-s SFLASH` write to serial flash,
  `-c` send UART break to connect, `-cf` auto-generate the flash header.
- At `--- please restart the device ---`, press the EVM reset button. If it hangs
  there forever, Ctrl+C is safe (nothing has been written yet); see ModemManager above.
- Success looks like: flash header written at offsets 0 and 4096, then the image at
  8192 with a progress bar, then `Done Metaimage: 0`.
- The tool appends logs to `batchstatus.txt` / `codes.txt` in the current directory.

Then power off, set functional mode, power on. Check with
`minicom -D /dev/ttyACM0 -b 115200` → `version` (exit: Ctrl-A, X).

## Firmware vs configuration

The **firmware** (`.appimage`) is flashed once. The **configuration** (`.cfg`) is a list
of CLI commands sent after every boot: chirp/frame timing, enabled antennas, CFAR
detection, field of view, which outputs to stream (`guiMonitor`), calibration, low
power, and finally `sensorStart`. It is not stored on the device. Tuning reference:
`$MMWAVE_SDK/docs/mmWave_Demo_Tuning_Guide.pdf`.

## Streaming (terminal)

```sh
cd ~/code/mmwave-tools/visualizer
../.venv/bin/python stream_check.py --log ../logs/run.bin   # send default cfg, stream, log
../.venv/bin/python stream_check.py --no-cfg                # sensor already running: just listen
../.venv/bin/python stream_check.py --replay ../logs/run.bin
python3 cfg_info.py $MMWAVE_SDK/examples/mmw_demo/mmwave_demo/profiles/profile_4T4R_tdm.cfg
```

Close minicom first: only one program can hold a port. With `lowPowerCfg 1` the CLI
may not respond once streaming; press reset before reconfiguring.

Derived numbers for every profile (SDK and local) are in [docs/profiles.md](docs/profiles.md).

## OOB demo data format

From `MmwDemo_transmitProcessedOutputTask()` in
`examples/mmw_demo/mmwave_demo/source/mmwave_demo.c`. Little-endian. 40-byte header
(magic `02 01 04 03 06 05 08 07`, version, total length, platform `0xA6844`, frame
number, CPU cycles, number of points, number of TLVs, subframe), then TLVs
(`uint32 type, uint32 length` + payload), padded to a multiple of 32 bytes.

| TLV type | Content | Payload |
|---|---|---|
| 1 | point cloud | `float32 x, y, z (m), velocity (m/s)` per point |
| 7 | point side info | `int16 snr, noise` per point, **0.01 dB** (see below) |
| 2 | range profile | `uint16` per range bin, log2 Q8: dB = raw × 6/256 |
| 5 | range-Doppler heatmap | `uint16`, range bins × Doppler bins, same units |
| 306 | stats | `uint32` processing µs, UART µs; `uint16` power ×4 (100 µW); `int16` temp ×4 (°C) |

Axes: y is boresight (away from the antennas), x is horizontal, z is up when the board
stands upright.

Notes: SNR/noise are in **0.01 dB** steps (not 0.1 dB as the header comment says), and
power readings are `0xFFFF` when USB-powered. Full list of quirks:
[docs/learnings.md](docs/learnings.md#firmware-quirks-and-limits).

## Visualizer

```sh
# terminal 1: backend (serial ports, cfg sending, record/replay) on :8765
cd ~/code/mmwave-tools/visualizer
../.venv/bin/python server.py

# terminal 2: frontend dev server with hot reload on :5173 (proxies /api and /ws to :8765)
cd ~/code/mmwave-tools/visualizer/web
npm install          # first time only
npm run dev
```

Open http://127.0.0.1:5173/. For a single-process setup, `npm run build` in `web/`
and the backend then serves `web/dist` itself at http://127.0.0.1:8765/.

Using it:

1. **Connect** (top bar) opens the data port; ports are auto-detected (XDS110
   interfaces 0 and 3) or set with `server.py --cli/--data`.
2. Pick a cfg (SDK profiles, or your own in `cfgs/`) or **Upload .cfg…**; the info
   table shows the derived range/velocity numbers before you send. **Send to device**.
   With low-power cfgs, press the EVM reset button before sending a new cfg (see below).
3. Four plot slots, each switchable: top view (X-Y), side view (Y-Z), range profile,
   range-Doppler heatmap, speed vs time (velocity of the fastest point per frame, with
   the peak over the last 60 s), temperatures. Points are colored by velocity (blue toward,
   gray static, red away) or SNR, with an optional fading trail. Hover for values.
4. **Record** writes raw bytes to `logs/frameData-*.bin`; **Replay** plays any log
   in `logs/` (including `stream_check.py --log` captures) at the chosen frame period.
5. The CLI box sends single commands (`version`, `sensorStop 0`, …).

Local cfgs in `cfgs/` (details and verification status in [docs/profiles.md](docs/profiles.md)):

- `person.cfg`: general person detection, moving and still (verified, 10 fps)
- `golf.cfg`: golf stage 1, club/ball speed up to ±67 m/s (verified, 19.8 fps)
- `profile_4T4R_tdm_sensitive.cfg`, `profile_4T4R_tdm_heatmap.cfg`: SDK profile with a
  lower threshold and/or the heatmap on

`cfg_info.py` (and the UI's config panel) warns before sending when a cfg breaks TI's
documented limits or the limits we hit on the device (chirp period, CFAR memory, UART
budget, velocity window, geometry commands); see
[docs/learnings.md](docs/learnings.md#firmware-quirks-and-limits).

**Low-power cfgs and the CLI:** with `lowPowerCfg 1` and the sensor running, the CLI
does not answer (`sensorStop 0` times out), so a new cfg can't be applied until the
EVM reset button is pressed. A software reset through the XDS110 would remove this
step (possible future work).

### Architecture

- **Backend** (`visualizer/server.py`, Python + aiohttp): owns both serial ports
  (reader thread → asyncio), sends cfgs, records raw logs, replays them, serves the
  built frontend, and pushes parsed frames over a WebSocket (`/ws`, JSON). Reuses
  `oob_protocol.py` and `cfg_info.py`. HTTP: `/api/ports`, `/api/cfgs`, `/api/cfg`,
  `/api/cfg-info`, `/api/logs`.
- **Frontend** (`visualizer/web/`, Vite + Svelte 5 + TypeScript, scaffolded with
  `npm create vite@latest -- --template svelte-ts`): uPlot for line plots, canvas
  for scatter and heatmap. Colors and tokens follow a validated palette with light
  and dark modes (follows the OS setting).

Why not Web Serial (browser opens the ports directly)? It works in Chrome on Linux,
but then Python can't hold the ports, which loses Python-side logging, replay and
numpy analysis.
